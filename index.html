2 · SBO 1.0 → Widget · Parameter-Mapping

Die bestehende SBO 1.0 routet alles über URL-Parameter (/international/services?country=AT&dealer=997&locale=de-DE&tenant=phs&brand=V&style=VW&sds=true&annualMileage=15000). So überträgst du jede dieser Parameter in die Widget-API:

country=AT → tenantConfig.country
Liefert die Backend-Bootstrap-Response. Steuert PLZ-/Telefon-Pattern. In Widget-API derzeit als Feld der TenantConfig modelliert (Phase 2).
dealer=997 → dealerId="997"
Direkter 1:1-Mapping. dealerId ist Pflicht-Prop am Widget, dient gleichzeitig als Storage-Key und als Bootstrap-Lookup-Key.
locale=de-DE → language="de"
Widget akzeptiert 2-stelligen ISO-Code. Region kommt aus country. Verfügbar: de · en · it in v1.1, weitere (fr, es) auf Anfrage.
tenant=phs → (Backend-intern)
Mandant nicht direkt im Widget — wird über dealerId aus dem Backend aufgelöst. Optional: präfix-basierte IDs wie "phs:997", wenn explizit gewünscht.
brand=V · brandCode=V → prefill.vehicle.brand="vw"
Markenfilter — vorausgewählte Marke beim Mount. SBO-1.0-Kürzel (V, A, S, Y, ...) muss auf Widget-Brand-IDs gemappt werden (vw, audi, skoda, cupra, ...). Mapping idealerweise im Backend-Bootstrap.
style=VW → theme="vw"
Marken-spezifisches CI. Aktuell verfügbar: neutral · vw. Audi, Cupra, Škoda, Seat, Porsche, Bentley folgen mit verifizierten CI-Werten.
vehicleAddedInSBO=true → prefillToken=<JWT>
Fahrzeug-Daten kommen aus SBO-Session → Backend signiert JWT mit Fahrzeug-Identifier (VIN, Marke, Modell, Kilometerstand) → Widget akzeptiert nur Signed Tokens für vertrauenswürdige Daten. Plain-Prefill ist für Kundendaten unsicher.
annualMileage=15000 → prefill.vehicle.annualMileage
Neues Feld auf BookingDraft.vehicle — wird ergänzt, wenn SBO 2.0 das benötigt. Aktuell ist nur mileage (aktueller Stand) modelliert.
driver=false → prefill.context.role
Treiber/Halter-Unterscheidung — z.B. für Texte ("Sie als Halter" vs. "Sie als Fahrer"). Modellierungsfrage: separates Context-Objekt im Prefill, oder Feature-Flag im TenantConfig.
sds=true → tenantConfig.features.serviceDataSystem
Service-Data-System-Flag. Feature-Flag-Pattern: TenantConfig.features.* schaltet pro Dealer einzelne UI-Pfade frei.

Variante 1 · Overlay über bestehende Buttons

Du hast bereits einen "Termin buchen"-Button auf der Seite (wie in der Info-Card oben) und möchtest, dass ein Klick darauf das Widget als Overlay öffnet. Ein einzelner Script-Tag plus ein onclick-Handler reichen.

Live
So bindest du das ein
<!-- Einmal im <head> oder vor </body> --> <script src="https://sbo-booking-widget.netlify.app/booking-widget.umd.js"></script> <!-- Beliebiger Button auf der Seite --> <button onclick="BookingWidget.open({ dealerId: 'senker' })"> Termin buchen </button>

Das UMD-Bundle registriert window.BookingWidget. Funktioniert auf jeder Seite, unabhängig vom CMS oder Framework.

import { BookingWidget } from '@dealer/booking-widget' function TerminButton() { const [open, setOpen] = useState(false) return ( <> <button onClick={() => setOpen(true)}>Termin buchen</button> <BookingWidget mode="overlay" dealerId="senker" open={open} onClose={() => setOpen(false)} /> </> ) }

Variante 2 · Fertiger CTA-Button

Wenn du keinen eigenen Button stylen möchtest, kannst du den vorgefertigten Pill-CTA verwenden. Er bringt sein gesamtes Styling inline mit, funktioniert in jedem CSS-Kontext und öffnet beim Klick automatisch das Overlay.

Live
So bindest du das ein
import { BookingCtaButton } from '@dealer/booking-widget' <BookingCtaButton dealerId="senker" /> // Optional anpassbar: <BookingCtaButton dealerId="senker" title="Service-Termin reservieren" subtitle="In 60 Sekunden online" bookingOptions={{ onBooked: (id) => track(id) }} />

Der CTA-Button ist eine React-Komponente und damit für React-/Next.js-Seiten gedacht. Für reine HTML-Seiten nutze stattdessen den Script-Tag mit eigenem Button-Styling (siehe Variante 1).

<!-- Variante für Nicht-React-Seiten: Eigener Button im CTA-Stil --> <script src="https://sbo-booking-widget.netlify.app/booking-widget.umd.js"></script> <button class="sbo-cta" onclick="BookingWidget.open({ dealerId: 'senker' })"> Werkstatt-Termin buchen </button>

Sag Bescheid, wenn du eine vanilla-HTML/CSS-Version mit Icon + Subtitle brauchst — ich liefere einen reinen HTML+CSS-Snippet ohne React-Dependency nach.

Variante 3 · Inline-Einbettung

Statt eines Overlays kann das Widget auch direkt in den Seitenfluss eingebettet werden — als statische Komponente, die sofort sichtbar ist. State und Persistenz bleiben identisch zum Overlay-Modus.

Live
So bindest du das ein
<!-- Script einmalig auf der Seite einbinden --> <script type="module" src="https://sbo-booking-widget.netlify.app/booking-widget.es.js"></script> <!-- Beliebig oft auf der Seite verwendbar --> <booking-widget dealer-id="senker" mode="inline" language="de" theme="vw" <!-- optional: "neutral" | "vw" --> ></booking-widget>

Custom Element: das Tag <booking-widget> wird vom Bundle automatisch registriert. Alles läuft im Shadow DOM, dein Seiten-CSS bleibt unberührt.

import { BookingWidget } from '@dealer/booking-widget' function ServicePage() { return ( <BookingWidget mode="inline" dealerId="senker" language="de" theme="vw" /> ) }

Variante 4 · Prefill & URL-Parameter

Daten von der Trägerseite ins Widget durchreichen — typische Anwendungen: die Trägerseite hat eine carlog-Session aufgelöst und kennt die Kundendaten, oder eine E-Mail-Einladung enthält Link-Parameter mit vorausgewählten Services und einem Termin. Reihenfolge: persistierter Draft < URL-Params < explizites prefill-Prop.

Live ausprobieren
… oder URL mit ?bw_*-Parametern in einem neuen Tab öffnen
So bindest du das ein
// Trägerseite hat carlog-Session aufgelöst und kennt den Kunden. <BookingWidget dealerId="senker" theme="vw" prefill={{ customer: { email: 'max@example.com', firstName: 'Max' }, vehicle: { brand: 'vw', model: 'polo' }, services: { selected: ['raederwechsel', 'oelwechsel'] }, step: 3, }} />

Übergebene Felder überschreiben den persistierten Draft. Wenn customer.email gesetzt ist, blendet das Widget den carlog-Login-Banner aus und zeigt stattdessen "Daten übernommen".

<!-- Prefill als JSON-Attribut --> <booking-widget dealer-id="senker" theme="vw" prefill='{"customer":{"email":"max@example.com"},"services":{"selected":["raederwechsel"]}}' ></booking-widget> // Oder via JS-API für das Overlay: BookingWidget.open({ dealerId: 'senker', theme: 'vw', prefill: { customer: { email: 'max@example.com' } } })
// E-Mail-Versand baut einen Link mit bw_*-Parametern: https://senker.at/service-buchen ?bw_email=max@example.com &bw_first_name=Max &bw_brand=vw &bw_model=polo &bw_services=raederwechsel,oelwechsel &bw_date=2026-11-08 &bw_time=10:00 &bw_step=3 // Das Widget liest sie automatisch beim Mount. // Deaktivieren: readUrlParams={false} // Eigener Präfix: urlParamPrefix="senker_"

Unterstützte Parameter: bw_brand, bw_model, bw_vin, bw_mileage, bw_services, bw_tire_storage, bw_date, bw_time, bw_replacement_car, bw_email, bw_first_name, bw_last_name, bw_phone, bw_address, bw_zip, bw_city, bw_country, bw_salutation, bw_message, bw_advisor, bw_step.

Variante 5 · Signed Token (vertrauenswürdiger Prefill)

Plain-prefill ist UX-Convenience und vom Browser manipulierbar — geeignet für unkritische Felder (Fahrzeug, Service-Auswahl). Für Kundendaten aus carlog oder E-Mail-Einladungen nimmt das Widget einen signierten JWT: der Token wird vom SBO-Backend ausgestellt, vom Widget nur dekodiert und beim Submit unverändert an das Backend zurückgereicht. Das Backend verifiziert Signatur + Verfall und zieht die Kundendaten ausschließlich aus dem Token.

Live ausprobieren
Mock-Token mit exp 15 min. In Produktion vom SBO-Backend signiert.
Im Widget: carlog-Banner zeigt "Daten übernommen", customer-Felder sind trusted.
So bindest du das ein
// 1. Trägerseite kennt carlog-User-ID // 2. Server-zu-Server: SBO-Backend signiert JWT POST /api/widget-tokens Authorization: Bearer <service-account-jwt> { user_id: "u_abc123", dealer_id: "senker", ttl_seconds: 900 } → 200 { token: "eyJhbGciOiJIUzI1NiJ9..." } // 3. Trägerseite gibt Token ans Widget weiter <BookingWidget prefillToken={token} dealerId="senker" /> // 4. Beim Submit wird der Token mitgeschickt POST /api/bookings { draft: {...}, prefill_token: "eyJhbGciOiJI..." } // 5. Backend verifiziert Token + überschreibt draft.customer aus Token

Security-Eigenschaften: Per DevTools modifizierte draft.customer-Felder werden vom Backend ignoriert. Token-Verfall macht abgefangene E-Mail-Links nach 15 min nutzlos. Replay innerhalb der TTL durch jti-Blacklist möglich.

import { BookingWidget } from '@dealer/booking-widget' async function BookingPage() { const token = await fetch('/api/widget-token').then(r => r.text()) return ( <BookingWidget dealerId="senker" theme="vw" prefillToken={token} /> ) }
<booking-widget dealer-id="senker" prefill-token="eyJhbGciOiJIUzI1NiJ9..." ></booking-widget> // Oder via JS-API: BookingWidget.open({ dealerId: 'senker', prefillToken: tokenFromServer, })

Phase 1 · Sicherheits- und Compliance-Bausteine

Was wir in v1 für Pilot-Reife eingebaut haben. Volle Architektur siehe README + docs/COOKIES.md.

✓ Signed Tokens
Vertrauenswürdiger Prefill
JWT-basiertes Prefill für Kundendaten. DevTools-Manipulation wirkungslos, Backend ist canonical source.
✓ Consent-aware
OneTrust-Integration
Liest window.OnetrustActiveGroups automatisch. Ohne functional consent → In-Memory-Storage, ohne analytics consent → keine Events.
✓ GA4 / GTM
dataLayer-Events
11 PII-freie Event-Typen für Step-Views, Service-Selections, Conversions. Trägerseiten-GTM picked sie up.
✓ PII-Minimization
Kein PII im Storage
E-Mail, Name, Adresse werden nie persistiert. Draft enthält nur Fahrzeug-, Service- und Termin-Auswahl.
✓ Versioning
Stabile CDN-Pfade
/v1/booking-widget.umd.js für Major-Pinning, /v1.x.y/ für exact-pinning. Breaking-Changes können nie versehentlich propagieren.
✓ SRI
Subresource Integrity
SHA-384-Hashes pro Bundle in /integrity.json. Kompromittierter CDN ≠ kompromittierte Trägerseiten.
